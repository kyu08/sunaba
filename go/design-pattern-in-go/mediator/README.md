## 概要

Mediatorは振る舞いに関するデザインパターンの一つで、オブジェクト間の直接的な依存関係を減らし、仲介者オブジェクトを通じて間接的に通信させるパターン。

> mediatorとは: 仲裁人、調停者 
>
> (https://ejje.weblio.jp/content/mediator)

オブジェクト間の結合度を下げ、個々のコンポーネントを再利用しやすくする。

## どんな問題を解決するのか

### 問題の具体例

鉄道駅のプラットフォーム管理システムを考える。

- 複数の列車（旅客列車、貨物列車など）が同じプラットフォームを使用する
- プラットフォームは一度に1つの列車しか利用できない
- 列車同士が直接通信してプラットフォームの空き状況を確認する場合:
  1. 各列車が他のすべての列車の状態を把握する必要がある
  2. 新しい列車タイプを追加するたびに、既存の全列車クラスを修正する必要がある
  3. 列車間の依存関係が複雑に絡み合い、保守が困難になる

理想: 列車同士が直接やりとりせず、プラットフォームの調整を中央で管理したい

## どう問題を解決するのか

### 解決策

Mediatorパターンでは以下のアプローチを取る:

1. 仲介者（Mediator）オブジェクトを導入し、オブジェクト間の通信をすべて仲介者経由にする
2. 各オブジェクト（Colleague）は他のオブジェクトを直接参照せず、仲介者のみを参照する
3. 仲介者が通信のロジックをカプセル化し、調整を一元管理する

## 使いどころ

### 適用すべき場面

| 場面 | 説明 |
|------|------|
| オブジェクト間の依存関係が複雑 | 多数のオブジェクトが相互に参照し合い、変更が困難な場合 |
| 再利用性を高めたい | コンポーネントを他のプログラムで再利用したいが、依存関係が多すぎて難しい場合 |
| 通信ロジックを一元管理したい | オブジェクト間の調整ロジックを1箇所に集約したい場合 |

### 具体的な適用例

- GUIコンポーネント間の連携: ダイアログ内のボタン、テキストフィールド、チェックボックス間の相互作用
- チャットルーム: ユーザー同士が直接通信せず、チャットルームオブジェクトを介してメッセージを送受信
- 航空管制: 複数の航空機が管制塔を通じて離着陸を調整
- イベント駆動システム: コンポーネント間のイベント配信をイベントバスが仲介

## 長所と短所

### 長所

- Single Responsibility Principle: 様々なコンポーネント間の通信を1箇所に集約できる
- Open/Closed Principle: 既存コンポーネントを変更せずに新しい仲介者を導入できる
- 結合度の低減: コンポーネント間の結合が緩くなり、再利用しやすくなる
- 通信フローの可視化: 通信ロジックが1箇所に集約されるため、フローを把握しやすい

### 短所

- 仲介者の肥大化: 全通信ロジックを集約するため、仲介者が「神オブジェクト」になりがち
