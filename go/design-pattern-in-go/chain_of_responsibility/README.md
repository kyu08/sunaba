## 概要
Chain of Responsibilityは振る舞いに関するデザインパターンの一つで、ハンドラーの連鎖に沿ってリクエストを渡すことができるパターン。各ハンドラーはリクエストを受け取ると、処理するか次のハンドラーに渡すかを決める。

リクエストの送信者と受信者を分離し、複数のオブジェクトにリクエストを処理する機会を与える。

## どんな問題を解決するのか

### 問題の具体例

病院の患者処理フローを考える。

- 患者は複数の部門（受付、医師、薬局、会計）を順番に回る必要がある
- 各部門で異なる処理が行われる
- すべての処理を1つのメソッドに詰め込む場合:
  1. コードが巨大になり保守が困難
  2. 処理の順序変更や新しい部門の追加が難しい
  3. 各部門の処理が密結合になる

理想: 各部門の処理を独立させ、柔軟に連鎖を構成したい

## どう問題を解決するのか

### 解決策

Chain of Responsibilityパターンでは以下のアプローチを取る:

1. 各処理を独立したハンドラーオブジェクトに分離する
2. 各ハンドラーは次のハンドラーへの参照を保持する
3. ハンドラーはリクエストを処理した後、次のハンドラーに渡すか判断する
4. クライアントは連鎖の先頭にリクエストを送るだけでよい

### 構造

```
┌────────────────────┐
│   <<interface>>    │
│     Department     │
├────────────────────┤
│ + execute(patient) │
│ + setNext(dept)    │
└────────────────────┘
          △
          │
 ┌────────┼────────┬────────────┐
 │        │        │            │
┌┴──────┐┌┴──────┐┌┴──────┐ ┌───┴────┐
│Recep- ││Doctor ││Medical│ │Cashier │
│tion   ││       ││       │ │        │
├───────┤├───────┤├───────┤ ├────────┤
│-next  ││-next  ││-next  │ │-next   │

    └────────┴────────┴──── 次のハンドラーを参照

連鎖: Reception → Doctor → Medical → Cashier
```

### 動作の流れ

```
1. 連鎖を構築（逆順で設定）

    Cashier (終端)
       ↑
    Medical.setNext(Cashier)
       ↑
    Doctor.setNext(Medical)
       ↑
    Reception.setNext(Doctor)

2. 患者がReceptionに到着

    Patient("abc")
         │
         ▼
    ┌─────────┐    ┌────────┐    ┌─────────┐    ┌─────────┐
    │Reception│───→│ Doctor │───→│ Medical │───→│ Cashier │
    │ 受付   │    │ 診察   │    │ 投薬    │    │ 会計    │
    └─────────┘    └────────┘    └─────────┘    └─────────┘
      登録処理       診察処理      薬の処方        支払処理

3. 各部門で処理後、次の部門へ自動的に引き継ぎ
```

## 使いどころ

### 適用すべき場面

| 場面 | 説明 |
|------|------|
| 複数の処理を順番に実行 | リクエストを複数のハンドラーで順番に処理する必要がある場合 |
| 処理の順序が動的に変わる | ハンドラーの組み合わせや順序を実行時に変更したい場合 |
| 処理者を事前に特定できない | どのハンドラーがリクエストを処理するか事前に分からない場合 |

### 具体的な適用例

- ミドルウェアチェーン: HTTPリクエストの認証、ロギング、圧縮などを順番に処理
- イベントハンドリング: GUIでのイベントバブリング（ボタン→パネル→ウィンドウ）
- ログレベル処理: DEBUG→INFO→WARN→ERRORの順でログを適切なハンドラーが処理
- 承認ワークフロー: 申請が担当者→マネージャー→部長と順番に回る

## 長所と短所

### 長所

- Single Responsibility Principle: 各ハンドラーが1つの責任に集中できる
- Open/Closed Principle: 既存コードを変更せずに新しいハンドラーを追加できる
- 処理順序の制御: 連鎖の順序を自由に設定・変更できる
- 疎結合: 送信者は受信者の詳細を知らなくてよい

### 短所

- リクエストが未処理になる可能性: 連鎖の終端まで達しても処理されない場合がある
- (追記)Interfaceが同じになる場合でしか利用できない
