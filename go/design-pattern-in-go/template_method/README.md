## 概要

Template Methodは振る舞いに関するデザインパターンの一つで、スーパークラス（基底クラス）でアルゴリズムの骨格を定義し、サブクラスがその構造を変えることなく特定のステップを上書きできるようにするパターン。

アルゴリズム全体の流れは固定しつつ、一部の処理だけをサブクラスでカスタマイズしたい場合に有効。

## どんな問題を解決するのか

### 問題の具体例

企業文書を分析するデータマイニングアプリを作成するシナリオを考える。

- PDF、DOC、CSVなど様々な形式の文書からデータを抽出する
- 最初はDOCファイルのみ対応 → 次にCSV → その後PDF対応と拡張

ある時点で気づく問題:

1. コードの重複: 3つのクラス（PDF、DOC、CSV用）に似たようなコードが存在する。データ形式を扱う部分は異なるが、データ処理・解析のコードはほぼ同じ
2. クライアント側の条件分岐: 処理オブジェクトのクラスに応じて適切な処理を選ぶ条件文だらけになる(とサイトには書いてあったが実装方法によっては条件文**だらけ**、にはならないかも？)

理想: アルゴリズムの構造をそのままに、コードの重複を取り除きたい

## どう問題を解決するのか

### 解決策

Template Methodパターンでは以下のアプローチを取る:

1. アルゴリズムを一連のステップに分解する
2. 各ステップをメソッドに変換する
3. 単一のテンプレート・メソッドからこれらのメソッドを順番に呼び出す

### ステップの種類

| 種類 | 説明 |
|------|------|
| 抽象ステップ | 全サブクラスで実装が必須 |
| オプションのステップ | デフォルト実装があり、必要な場合だけ上書きできる |
| フック | 空のデフォルト実装を持つオプションのステップ。アルゴリズムの重要なステップの前後に配置され、サブクラスに拡張箇所を提供 |

### 構造

```
┌─────────────────────────────────────┐
│         Abstract Class              │
├─────────────────────────────────────┤
│ + templateMethod()  ←──── 変更不可  │
│ + step1()           ←──── 抽象      │
│ + step2()           ←──── 抽象      │
│ + step3()           ←──── デフォルト│
│ + hook()            ←──── 空実装    │
└─────────────────────────────────────┘
              △
              │
    ┌─────────┴─────────┐
    │                   │
┌───────────┐     ┌───────────┐
│ Concrete  │     │ Concrete  │
│  Class A  │     │  Class B  │
├───────────┤     ├───────────┤
│ + step1() │     │ + step1() │
│ + step2() │     │ + step2() │
│           │     │ + step3() │
└───────────┘     └───────────┘
```

## 使いどころ

### 適用すべき場面

| 場面 | 説明 |
|------|------|
| アルゴリズムの特定ステップのみ拡張させたい | 全体の構造は変えずに、特定のステップだけをサブクラスでカスタマイズ可能にしたい場合 |
| ほぼ同じアルゴリズムのクラスが複数ある | 少数の違いを除いてほとんど同じ処理をするクラスが複数存在し、重複コードを削減したい場合 |
| アルゴリズムの流れを固定したい | 処理の順序や構造を保証しつつ、詳細な実装は柔軟にしたい場合 |

### 具体的な適用例

- フレームワークの拡張ポイント: ライフサイクルフックやミドルウェア
- データ処理パイプライン: ETL処理、ファイル変換
- テストフレームワーク: setUp/tearDownパターン
- ゲームAI: 基本的な行動パターンは同じだが、種族ごとに詳細が異なる

## 長所と短所

### 長所

- クライアントはアルゴリズムの特定部分のみを上書き可能。他部分への変更の影響を受けにくい
- 重複コードをスーパークラスに集約できる
- Open/Closed Principleに従う（新しいバリエーションはサブクラス追加で対応）

### 短所

- 与えられたアルゴリズムの骨組みが、一部のクライアントにとっては制約になる可能性
- サブクラスでステップのデフォルト実装を抑制すると、リスコフの置換原則違反の可能性
- ステップ数が多いほど、テンプレート・メソッドの保守が困難に

（たぶんただinterfaceを呼び出す設計との差分はデフォルト実装を利用可能な点なんだろうなー。あとはhookのような拡張ポイントの存在も差分か。）
